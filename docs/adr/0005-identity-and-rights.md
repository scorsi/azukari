# ADR 0005 — Identity and rights

Status: Accepted — 2026-10-29. File key names superseded by ADR 0011; SVID reload superseded by ADR 0016.

## Context

Every connection is mutual TLS with X.509-SVIDs from the internal CA (owner, 2026-10-29: no
bearer tokens, not even as a first step). The CA's contract (hanko ADR-0004, ADR-0005):
SPIFFE IDs `spiffe://<trust-domain>/<host>/<service>`, a single URI SAN, no DNS SAN, ECDSA
P-256, 24 h lifetime renewed at half, three files per identity (`svid.pem`, `key.pem`,
`bundle.pem`) readable by the service's group, the unit reloaded after a renewal. The CA
decides which host may hold which ID; nothing is registered at runtime.

A `backup` bucket gives each node its own namespace, add-only (ADR 0001, 0003). Deletion and
other administration go through a local socket only (ADR 0001).

## Options considered

Who may use a bucket:

- **An explicit list of SPIFFE IDs per bucket** in the store's configuration: two independent
  gates (the CA says who may hold an ID, the store says which IDs may use a bucket); one line
  per node, generated by the deployment.
- **A pattern** (`spiffe://<td>/*/azukari-backup`): adding a node needs only the CA's
  configuration, but a too broad entry there opens the bucket.

How a renewed SVID or bundle is picked up by the store:

- **Re-read on `SIGHUP`** (the CA's reload of the unit) and at start.
- **Watch the files' modification times**: works without the reload, a timer to tune.

## Decision

- **Files**: both sides take `svid_file`, `key_file`, `bundle_file` and the `trust_domain`.
  `azukari-backup` is a oneshot and reads them at start. `azukari-server` reads them at start
  and on `SIGHUP`: a new certificate serves new handshakes, a new bundle verifies new
  handshakes; open connections are not cut. A reload that fails (unreadable file, key not
  matching the certificate) keeps the previous material and logs an error.
- **Verification**, written once in the shared library and used by both sides: the chain
  verifies against the current bundle with the right extended key usage, the leaf is not a
  CA, it carries exactly one URI SAN, a valid SPIFFE ID in the configured trust domain.
  - `azukari-backup` then requires the server's ID to equal its configured `server_id`; no
    DNS name is checked.
  - `azukari-server` maps the client's ID to its rights below. An ID outside the trust
    domain or without a grant fails every request with 403 `forbidden`.
- **Grants: an explicit list of IDs per bucket** (owner, 2026-10-29):

  ```toml
  [[buckets]]
  name = "backup"
  type = "backup"
  # …
  nodes = [
    "spiffe://example.org/node-a/azukari-backup",
    "spiffe://example.org/node-b/azukari-backup",
  ]
  ```

  In a `backup` bucket a listed ID may `put`, `get`, `missing` and `list`, only in the
  namespace named by the ID's `<host>` segment, which must be a valid key segment (ADR 0003).
  Nothing else exists to grant on that type; other types define their rights in their ADRs.
- **Local administration**: a Unix socket in the store's runtime directory, mode `0660`,
  group `azukari-admin` (static, created by the module, the deployment adds operators).
  Filesystem permissions are the authorisation; the store logs the caller's uid
  (`SO_PEERCRED`) on every call. The calls are defined with what they administer (retention
  ADR); the socket never listens on the network.
- **No unauthenticated port** except the loopback `/metrics` listener (observability ADR).

## Consequences

- Adding a node takes two lines in the deployment: its ID in the CA's configuration and in
  the bucket's `nodes`.
- A backup node can restore only its own namespace. Restoring a dead node's data onto a host
  with another name means issuing it the dead node's ID for the time of the restore (a CA
  configuration change); a read grant across namespaces is left to a later ADR if that
  becomes routine.
- If the CA is unreachable for longer than an SVID's lifetime, backups fail at the handshake;
  the store's per-node freshness (observability ADR) shows it.
- Tests issue their own SVIDs from a test CA with the same profile: azukari depends on the
  file contract, not on the CA's code.
